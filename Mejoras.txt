Este documento recoge el analisis critico del codigo fuente completo del proyecto
ForceVector v2.0 y propone mejoras ordenadas por prioridad e impacto.

El analisis abarca:
  - forcevector/main.py
  - forcevector/functions/ (orchestrator, llm_client, config, database, ui)
  - forcevector/agents/ (recon, scan, exploit, auth, web, ad, db, privesc, report, agent_utils)
  - forcevector/agents/post_exploitation/ (agent, post_exploit_agent, skills/)
  - forcevector/config/config.json
  - forcevector/frontend/index.html
  - README.md / REQUIREMENTS_KALI.txt

================================================================================
SECCION 1: VULNERABILIDADES DE SEGURIDAD CRITICAS
================================================================================

[C-01] CREDENCIAL EN TEXTO PLANO EN config.json
Prioridad: MUY ALTA
-------------------------------------------------
Archivo:  forcevector/config/config.json
Problema: La contrasena de PostgreSQL ("155007287+Cid$") esta en texto claro
          directamente en el fichero de configuracion JSON, que puede quedar
          incluido en el repositorio Git accidentalmente.
Impacto:  Exposicion total de la base de datos si el repositorio es publico
          o si el fichero se comparte.
Mejora:
  a) Anadir config.json a .gitignore desde el principio.
  b) Sustituir la contrasena en texto plano por una variable de entorno:
     en config.json guardar solo {"database": {"password": ""}}
     y en database.py resolverla con:
     os.environ.get("FORCEVECTOR_DB_PASS", db_conf.get("password"))
  c) Alternativamente, usar python-dotenv y un archivo .env que tambien
     este en .gitignore.

[C-02] INYECCION SQL POTENCIAL EN ask_ollama()
Prioridad: MUY ALTA
-----------------------------------------------
Archivo:  forcevector/functions/llm_client.py (linea 118)
Problema: La consulta SQL generada por el LLM se ejecuta directamente con
          cur.execute(sql_query). La blocklist de palabras clave
          (drop|delete|truncate) puede ser evadida con mayusculas creativas,
          Unicode, comentarios SQL, etc.
Impacto:  Ejecucion de consultas arbitrarias en la base de datos.
Mejora:
  a) Ejecutar las consultas del LLM con un usuario de PostgreSQL de
     solo lectura (READ ONLY), no con el usuario postgres superadmin.
  b) Reemplazar la blocklist por una allowlist de operaciones permitidas
     (solo SELECT) y rechazar cualquier otra instruccion.
  c) Envolver la ejecucion en una transaccion que se haga rollback
     automatico tras la lectura.

[C-03] EJECUCION ARBITRARIA DE COMANDOS EN SANDBOX (os.system)
Prioridad: ALTA
---------------------------------------------------------------
Archivo:  forcevector/agents/agent_utils.py (linea 159)
          forcevector/main.py (linea 133)
Problema: os.system(cmd) se usa para ejecutar comandos recibidos desde el
          mini-REPL del Sandbox sin ningun saneamiento. Un error de prompt
          injection podria ejecutar comandos del SO arbitrarios.
Mejora:
  a) Sustituir os.system(cmd) por subprocess.run(shlex.split(cmd))
     para evitar expansion de shell.
  b) Validar el formato del comando antes de ejecutarlo (allowlist de
     herramientas permitidas: recon, scan, post...).
  c) Registrar en log cada comando ejecutado en el REPL del Sandbox.

[C-04] CREDENCIALES MSFRPC POR DEFECTO
Prioridad: ALTA
---------------------------------------
Archivo:  forcevector/config/config.json (password: "msf")
          forcevector/main.py (linea 117)
Problema: La contrasena de MSFRPC es "msf" (valor por defecto), hardcodeada
          como fallback. Si el puerto 55552 es accesible desde la red,
          cualquier atacante puede tomar control del demonio MSF.
Mejora:
  a) Generar una contrasena aleatoria segura al iniciar el sistema por
     primera vez y guardarla en config.json (minimo 24 caracteres).
  b) Forzar binding exclusivo a 127.0.0.1 y validarlo siempre.
  c) Alertar al usuario si detecta que se usa la contrasena por defecto.

SECCION 2: CALIDAD DEL CODIGO Y DEUDA TECNICA
================================================================================

[D-01] DUPLICACION DE CODIGO: DOS IMPLEMENTACIONES DE POST-EXPLOTACION
Prioridad: ALTA
-----------------------------------------------------------------------
Archivos: forcevector/agents/post_exploitation/agent.py
          forcevector/agents/post_exploitation/post_exploit_agent.py
Problema: Existen dos archivos con la misma logica (_load_skills,
          _record_successful_compromise, run_post_exploitation). La diferencia
          es que agent.py tiene un bucle ReAct iterativo y post_exploit_agent.py
          solo hace una iteracion. orchestrator.py importa "post_exploit_agent"
          pero agent_utils.py importa "agent". Esto genera confusion y bugs.
Mejora:
  a) Consolidar en un unico modulo: agents/post_exploitation/agent.py
     con el bucle ReAct.
  b) Eliminar post_exploit_agent.py o convertirlo en thin wrapper.
  c) Actualizar orchestrator.py para importar desde el mismo lugar
     que el Sandbox.

[D-02] HARDCODING DE CODIGOS ANSI EN MULTIPLES ARCHIVOS
Prioridad: MEDIA-ALTA
---------------------------------------------------------
Archivos: exploit_agent.py, agent_utils.py, post_exploitation/agent.py,
          post_exploitation/skills/*.py, report_agent.py
Problema: Los codigos de color ANSI se definen como literales en cada archivo
          (\033[91m, \033[92m, etc.) en vez de importar las constantes
          centralizadas de functions/ui.py. Hay al menos 4 esquemas de color
          distintos en uso simultaneo.
Mejora:
  a) En todos los agentes, sustituir los literales ANSI por imports:
     from functions.ui import COLOR_ERROR, COLOR_SUCCESS, COLOR_RESET...
  b) Anadir las constantes que falten a ui.py (COLOR_DEBUG, COLOR_WARN, etc.).
  c) Anadir comprobacion isatty() para desactivar colores si no hay terminal.

[D-03] MANEJO DE ERRORES SILENCIOSO (bare except / pass)
Prioridad: MEDIA-ALTA
---------------------------------------------------------
Archivos: post_exploitation/agent.py (linea 60), orchestrator.py (linea 130)
Problema: Bloques "except Exception: pass" que silencian errores sin registro.
          En agent.py linea 60, el error al guardar el estado de compromiso
          se ignora silenciosamente.
Mejora:
  a) Reemplazar todos los "pass" de except por al menos un print o log.
  b) Implementar el modulo logging con niveles en vez de prints.

[D-04] AUSENCIA TOTAL DE SISTEMA DE LOGGING ESTRUCTURADO
Prioridad: MEDIA-ALTA
---------------------------------------------------------
Archivos: Todo el proyecto
Problema: El proyecto usa print() para toda la telemetria. No hay modulo
          logging configurado. Esto impide filtrar por nivel, redirigir a
          fichero sin afectar a la UI, o anadir timestamps automaticos.
Mejora:
  a) Crear forcevector/functions/logger.py con dos handlers:
     - StreamHandler (consola) con formato de colores ANSI
     - FileHandler (logs/forcevector.log) sin colores, con timestamp
  b) Sustituir los print() de diagnostico por logging.info/warning/error().
  c) Anadir al config.json un campo "log_level": "INFO" configurable.

[D-05] PARSING NMAP POR REGEX EN VEZ DE XML
Prioridad: MEDIA
--------------------------------------------
Archivo:  forcevector/agents/scan_agent.py
Problema: El parser usa regex sobre texto plano. Nmap genera XML nativo con
          -oX que es mas robusto y sin riesgo de romper con cambios de
          formato en versiones de nmap.
Mejora:
  a) Cambiar el comando nmap para anadir -oX - (salida XML a stdout).
  b) Parsear el XML con xml.etree.ElementTree o usar python-libnmap.
  c) Esto permitira capturar mas informacion (scripts NSE, CPE, etc.).

[D-06] AUSENCIA DE requirements.txt EJECUTABLE
Prioridad: MEDIA
-----------------------------------------------
Archivos: Raiz del proyecto, REQUIREMENTS_KALI.txt
Problema: Las dependencias Python estan documentadas en un archivo .txt de
          texto libre que no es ejecutable con pip. La instalacion es manual
          y propensa a errores de version.
Mejora:
  a) Crear forcevector/requirements.txt con versiones fijadas:
     requests>=2.31.0
     psycopg2-binary>=2.9.9
     pymetasploit3>=1.0.3
     jinja2>=3.1.3
     weasyprint>=61.2
  b) Actualizar REQUIREMENTS_KALI.txt para referenciar este fichero.

[D-07] PATRON DE IMPORTACION TARDIA (LAZY IMPORTS) INCONSISTENTE
Prioridad: MEDIA
-----------------------------------------------------------------
Archivos: forcevector/functions/orchestrator.py (lineas 183, 199, 219)
          forcevector/functions/llm_client.py (linea 117)
Problema: Varios modulos se importan dentro de funciones en lugar de en el
          nivel del modulo. Esto oculta dependencias, retrasa la deteccion
          de modulos faltantes y confunde a herramientas de analisis estatico.
Mejora:
  a) Mover los imports al nivel superior del modulo siempre que sea posible.
  b) Para dependencias opcionales, usar try/except en el nivel del modulo.

SECCION 3: ROBUSTEZ Y FIABILIDAD
================================================================================

[R-01] VECTOR DATABASE SIN USO REAL DE EMBEDDINGS (RAG VACIO)
Prioridad: ALTA (impacto academico del TFM)
--------------------------------------------------------------
Archivo:  forcevector/functions/database.py
Problema: La tabla agent_memory tiene columna "embedding vector(4096)" pero
          nunca se insertan embeddings reales. La busqueda vectorial semantica
          (ventaja principal de pgvector) no esta implementada. La BD funciona
          como un almacen de texto plano normal.
Impacto:  La propuesta de RAG vectorial del README no esta implementada,
          lo cual es un gap significativo para el TFM.
Mejora:
  a) Integrar el modelo de embeddings (nomic-embed-text:v1.5 ya listado
     en README) para generar vectores con cada registro insertado.
  b) Implementar busqueda semantica real en Fase 3:
     SELECT content FROM agent_memory
     ORDER BY embedding <-> query_embedding LIMIT 5;
  c) Esto mejoraria la calidad del modelado de amenazas al recuperar
     contexto similar de operaciones anteriores.

[R-02] SIN TIMEOUT EN ESCANEO NMAP (posible bloqueo indefinido)
Prioridad: ALTA
----------------------------------------------------------------
Archivo:  forcevector/agents/scan_agent.py (lineas 26-31, 40-47)
Problema: subprocess.run() para nmap no tiene timeout configurado. Un escaneo
          UDP con -T4 -F puede tardar varios minutos y bloquear indefinidamente.
Mejora:
  a) Anadir timeout al subprocess.run():
     subprocess.run([...], timeout=300, ...)
  b) Capturar subprocess.TimeoutExpired y continuar con datos parciales.
  c) Informar al usuario del timeout con un mensaje claro.

[R-03] CONEXION DE BASE DE DATOS SIN POOL NI RECONEXION AUTOMATICA
Prioridad: MEDIA-ALTA
-------------------------------------------------------------------
Archivos: forcevector/functions/database.py, forcevector/main.py
Problema: Se crea una unica conexion psycopg2 al inicio y se pasa como
          parametro por toda la cadena. Si la conexion se pierde, todas
          las operaciones fallan sin reconexion automatica.
Mejora:
  a) Usar psycopg2.pool.ThreadedConnectionPool para gestion de conexiones.
  b) Anadir connection keepalive:
     keepalives=1, keepalives_idle=30, keepalives_interval=10

[R-04] GUARDARRAIL ANTI-ALUCINACION SOLO EN RCE, NO EN OTROS AGENTES
Prioridad: MEDIA-ALTA
----------------------------------------------------------------------
Archivos: agents/auth_agent.py, agents/web_agent.py, agents/ad_agent.py,
          agents/db_agent.py, agents/privesc_agent.py
Problema: El guardarrail (verificacion de que el modulo generado existe en
          disco) solo esta en _execute_rce_metasploit(). Los agentes auth,
          web, ad, db, privesc generan comandos sin ninguna validacion.
Mejora:
  a) Crear _validate_command(command, category) en agent_utils.py que
     verifique que el binario principal existe en el PATH.
  b) Para comandos con modulos MSF, aplicar _verify_msf_module().
  c) Registrar en debug todas las ejecuciones de agentes especializados.

[R-05] INICIO MSFRPC CON os.system() SIN VERIFICACION DE PRIVILEGIOS
Prioridad: MEDIA
----------------------------------------------------------------------
Archivo:  forcevector/main.py (linea 133)
Problema: os.system() se ejecuta sin verificar si el usuario tiene privilegios.
          Si falla silenciosamente, el sistema espera 15 segundos antes de
          reportar el fallo.
Mejora:
  a) Usar subprocess.Popen con stderr capturado para detectar errores
     de permisos inmediatamente.
  b) Reducir el tiempo de espera maximo a uno configurable.

[R-06] FALTA DE VALIDACION DE ENTRADA EN EL REPL
Prioridad: MEDIA
-------------------------------------------------
Archivo:  forcevector/main.py (lineas 179-196)
Problema: Los comandos "recon <CIDR>", "scan <IP>", etc. no validan el formato
          del argumento. Un CIDR malformado causa error criptico en nmap.
Mejora:
  a) Para CIDR: usar ipaddress.ip_network(target, strict=False)
  b) Para IP:   usar ipaddress.ip_address(target)
  c) Mostrar mensajes descriptivos si el formato no es valido.

SECCION 4: ARQUITECTURA Y DISENO
================================================================================

[A-01] DISCREPANCIA ENTRE README Y CODIGO REAL IMPLEMENTADO
Prioridad: ALTA (impacto en evaluacion del TFM)
------------------------------------------------------------
Problema: El README.md describe una arquitectura v2.0 con FastAPI, Redis, JWT,
          WebSocket, scripts de instalacion automatica y sincronizacion CVE.
          Sin embargo, el codigo real es una CLI REPL sin ninguno de esos
          componentes. El frontend/index.html existe pero no tiene backend.
Impacto:  El README es enganoso. Para un TFM puede ser un problema en la
          evaluacion.
Mejora:
  a) (Corto plazo) Actualizar README.md para reflejar la arquitectura
     real: CLI + Ollama + PostgreSQL + MSF RPC.
  b) (Largo plazo) Implementar el backend FastAPI minimo que sirva el
     frontend y exponga los endpoints documentados.
  c) Marcar claramente en el README que es "implementado", "en desarrollo"
     y "planificado para v3.0".

[A-03] MEZCLA DE RESPONSABILIDADES EN orchestrator.py
Prioridad: MEDIA
------------------------------------------------------
Archivo:  forcevector/functions/orchestrator.py
Problema: El modulo mezcla logica de coordinacion de agentes con logica de
          presentacion (prints de estado). Viola la separacion de
          responsabilidades y dificulta los tests.
Mejora:
  a) Separar la logica de presentacion usando callbacks o el sistema de
     logging estructurado (D-04).

[A-04] FALTA DE PERSISTENCIA ENTRE SESIONES
Prioridad: MEDIA
--------------------------------------------
Problema: El estado de la sesion (hosts_activos, objetivos_analizados) vive
          solo en variables locales. Si el proceso se reinicia, se pierde
          todo el progreso.
Mejora:
  a) Guardar el estado en logs/session_state.json con:
     {phase, target, hosts, vectors_analyzed, ...}
  b) Al arrancar, ofrecer al usuario "Reanudar sesion anterior" vs "Nueva".
  c) Marcar cada fase como PENDING/IN_PROGRESS/COMPLETED.

[A-05] AUSENCIA DE TESTS AUTOMATIZADOS
Prioridad: ALTA (impacto en evaluacion del TFM)
-----------------------------------------------
Problema: No existe ningun directorio tests/ ni archivos de test. Para un TFM
          de seguridad informatica, la ausencia de tests es una carencia notable
          y dificulta la validacion de los guardarrailes.
Mejora:
  a) Crear tests/test_scan_parser.py para validar _parse_nmap_output()
     con salidas de nmap de ejemplo (fixtures).
  b) Crear tests/test_hallucination_guard.py para verificar que
     _verify_msf_module() detecta correctamente modulos falsos.
  c) Crear tests/test_category_detection.py para _determinar_categoria().
  d) Usar pytest: pytest tests/ -v

[U-01] EL FRONTEND index.html NO ESTA CONECTADO AL BACKEND
Prioridad: ALTA (impacto visual en la demo)
-----------------------------------------------------------
Archivo:  forcevector/frontend/index.html (59 KB)
Problema: Existe un frontend web completo pero no hay servidor que lo sirva
          ni API a la que conectarse. La UI es completamente estatica.
Mejora:
  a) (Minimo) python3 -m http.server 8080 --directory frontend/
  b) (Optimo) Implementar un endpoint FastAPI que sirva el HTML y exponga
     una API WebSocket para streaming del output del REPL.

[U-02] COMANDO HELP INSUFICIENTE
Prioridad: MEDIA
---------------------------------
Archivo:  forcevector/main.py (linea 151)
Problema: El mensaje de ayuda muestra solo una linea. No existe un comando
          "help" que muestre descripcion de cada opcion con ejemplos.
Mejora:
  a) Anadir comando "help" al REPL con descripcion completa de comandos.
  b) Si el usuario escribe un comando desconocido, sugerir el mas parecido.

[U-03] SIN BARRA DE PROGRESO DURANTE ESCANEOS LARGOS
Prioridad: MEDIA-BAJA
-----------------------------------------------------
Problema: Durante escaneos UDP el proceso puede durar varios minutos sin
          ninguna retroalimentacion visual.
Mejora:
  a) Anadir un spinner usando la libreria rich o tqdm.
  b) Ejecutar nmap con -v y capturar salida en tiempo real.

[U-04] MENSAJES DE ERROR POCO DESCRIPTIVOS EN FALLOS DE CONEXION
Prioridad: MEDIA-BAJA
-----------------------------------------------------------------
Problema: Cuando falla la conexion con Ollama o PostgreSQL, se muestra la
          excepcion tecnica cruda.
Mejora:
  a) Mapear errores comunes a mensajes amigables:
     "Connection refused" -> "Ollama no esta corriendo. Ejecuta: ollama serve"
  b) Incluir el comando de diagnostico sugerido.

Prioridad: ALTA (impacto en resultados del TFM)

Archivo:  forcevector/agents/exploit_agent.py (_log_hallucination)

Prioridad: ALTA (valor academico)

Mejora:

     los ejecute con diferentes modelos y registre tasa de alucinacion,
     tiempo de respuesta y calidad del script generado.
  b) Guardar resultados en logs/benchmark_YYYYMMDD.json
  c) Generar tablas comparativas para el TFM con datos reales.

[M-03] EL LOG DEBUG NO TIENE ANALISIS AUTOMATICO
Prioridad: MEDIA-ALTA
-------------------------------------------------
Archivo:  forcevector/logs/tfm_llm_debug.log (620 KB)

  b) Crear analyze_logs.py que procese el JSONL y genere estadisticas.
  c) Exportar en CSV para importar en Excel/Jupyter.

Mejora:   a) Anadir "lport" al config.json o generarlo dinamicamente.

          __pycache__/
          *.pyc
          config/config.json
          logs/
